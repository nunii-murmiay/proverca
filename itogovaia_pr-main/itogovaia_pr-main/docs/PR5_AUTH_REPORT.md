## Как запустить

Сначала в папке проекта запускается сервер:

```
node api/mock-server.js --ttl 60
```

Параметр `--ttl 60` делает access-токен коротким (60 секунд), чтобы было удобно проверять обновление сессии.

Потом в другом окне запускается приложение:

```
flutter run -d chrome
```

Адрес API: `http://localhost:8080/api`.

Для проверки ролей используются учебные учётки.

| Логин | Пароль | Роль |
|---|---|---|
| reader | reader123 | Покупатель |
| librarian | librarian123 | Менеджер |
| admin | admin123 | Администратор |

Различия ролей видно по меню. У покупателя есть экран «Мои покупки» и нет управления каталогом. У менеджера есть «Продажи», работа с клиентами и редактирование справочников. У администратора дополнительно есть «Пользователи» и «Статистика», а также полное удаление и восстановление записей.

## Жизненный цикл токена от входа до выхода

Пользователь открывает форму входа и вводит логин и пароль. Пароль на клиенте не хешируется. Хеш считает только сервер.

Если данные верные, сервер отдаёт два токена и сведения о пользователе. Короткий токен называется access. Им подписывают обычные запросы к API. Длинный токен называется refresh. Им получают новую пару, когда access истёк. Обычно access живёт около 15 минут. Если сервер запущен с `--ttl 60`, access живёт 60 секунд.

Оба токена и профиль пользователя сохраняются в localStorage браузера. Поэтому после обновления страницы человек остаётся в системе.

При каждом запросе к API клиент добавляет заголовок Authorization с access-токеном. Если access уже недействителен, сервер отвечает кодом 401. Клиент один раз обновляет пару через refresh и повторяет тот же запрос. Пользователь этого почти не замечает.

Если refresh использовать не удалось, приложение выходит из системы. Бесконечного круга запросов нет: адреса вида `/auth/...` при обновлении не трогаются, а повтор обычного запроса делается максимум один раз.

Если человек три минуты ничего не делает, сессия завершается. За 30 секунд до этого показывается предупреждение. Время последнего действия тоже лежит в localStorage, поэтому проверка работает и после обновления страницы.

Через два часа от момента входа сессия всё равно завершается, даже если человек всё это время был активен.

При выходе токены стираются из хранилища, refresh на сервере аннулируется, открывается экран входа.

## Почему клиентская проверка прав не является защитой

На Flutter Web код приложения и localStorage доступны пользователю. Скрытие кнопок и проверка роли на клиенте делают интерфейс удобнее: человек не видит чужие пункты меню и не шлёт лишние запросы. Но это не защита данных.

Профиль в ключе `flutter.auth_user` можно изменить вручную в DevTools. Тогда интерфейс может показать кнопки другой роли. Настоящий access-токен при этом не меняется. Сервер смотрит на токен и на роль в своей базе. Если операция запрещена, он отвечает кодом 403.

Клиентская проверка нужна для удобства. Настоящая защита выполняется только на сервере при каждом запросе.

## Проверка пункта 17

Смысл проверки простой. Если кнопку спрятали в интерфейсе, это ещё не значит, что операция запрещена по-настоящему. Настоящий запрет делает только сервер.

Сначала нужно войти покупателем: логин `reader`, пароль `reader123`. В меню не должно быть пунктов «Пользователи» и «Статистика».

Дальше открываются DevTools, вкладка Application, раздел Local Storage, адрес сайта. Там находится ключ `flutter.auth_user`. В значении нужно заменить `"role":"reader"` на `"role":"admin"`, сохранить изменение и сразу обновить страницу через F5.

В меню могут появиться пункты администратора, потому что интерфейс смотрит на сохранённый профиль. Если открыть «Пользователи», сервер всё равно ответит отказом. Во вкладке Network у запроса к `/api/users` будет код 403. В интерфейсе тоже будет сообщение про отказ в доступе.

Почему так. В localStorage лежит кэш профиля для удобства экрана. Его можно поменять вручную, и кнопки появятся. Но access-токен остаётся токеном покупателя. Сервер смотрит на токен и на роль в своей базе и отклоняет запрещённую операцию кодом 403.

## Что реализовано в работе

Есть формы входа и регистрации с проверкой обязательных полей. После входа открывается главный экран, в шапке видны ФИО и роль. Выход удаляет токены и возвращает на экран входа. После перезагрузки страницы пользователь остаётся в системе, потому что токены читаются из localStorage. При неверном пароле показывается понятное сообщение. К защищённым запросам добавляется заголовок Authorization.

Пароль при регистрации проверяется по ходу ввода: не меньше 8 символов, нужна цифра и спецсимвол. Есть три роли с разным набором функций. Маршруты защищены: чужой адрес открывает экран «Доступ запрещён». Недоступные пункты меню и кнопки скрыты. После входа можно вернуться на тот адрес, с которого отправили на логин. Ответ 403 показывается понятным сообщением в интерфейсе.

Access-токен обновляется автоматически при ответе 401. Сессия завершается после трёх минут бездействия, с предупреждением за 30 секунд. Через два часа от входа сессия завершается даже при активности. При неудачном обновлении токена выход происходит без зацикливания запросов. Проверка пункта 17 показывает, что клиентская «защита» не настоящая. Права ролей покрыты тестами в файле `test/permissions_test.dart`.

## Тесты

Запуск:

```
flutter test test/permissions_test.dart
```

Тесты проверяют, что покупатель видит каталог, но не управляет им; что свои покупки доступны только покупателю; что менеджер может оформлять продажи и работать с клиентами; что hard-delete, restore, пользователи и статистика доступны только администратору; что администратор умеет то же по каталогу и продажам, что менеджер; что гость перенаправляется на вход; что покупатель не попадает на экраны пользователей и продаж; что менеджер не попадает на «Мои покупки» и статистику.

## Главный вывод

На Flutter Web код приложения и localStorage доступны пользователю. Скрытие кнопок и проверка роли на клиенте делают интерфейс удобнее, но не защищают данные. Настоящая защита выполняется только на сервере: он проверяет токен и роль при каждом запросе и при необходимости отвечает 401 или 403.
